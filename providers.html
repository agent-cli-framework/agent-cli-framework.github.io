Providers

A provider is one directory that projects a platform's API onto the command surface. Every provider meets the same contract and the same conformance suite, whichever tier it belongs to.

Three tiers

native

Maintained by the project. Every release runs their full suite, including live smoke tests against real tenants.

contributed

Maintained by the people named in the plugin and in CODEOWNERS. Same contract, same conformance rules; the project reviews only for contract and boundary questions.

private

A fork's own providers, under a prefix upstream never commits to. Pulling upstream never conflicts with them, and upstream CI refuses pull requests that touch the prefix.

Tier is a property of the directory a plugin lives in, never something the plugin declares. The provider index is generated at build time by scanning those directories, so adding a provider in any tier is creating a directory. Nothing in package.json or the framework's source changes.

Writing one

Start from the platform's API specification. Every serious SaaS API publishes a machine-readable description of itself, and a provider is a mechanical projection of that description onto the command surface: entities become topics, operations become commands, the specification's field types become flags, and its example values become fixtures. That is work a coding agent does well, and the conformance suite decides when the result is done.

A provider directory holds a plugin definition, a credential schema, a client, an error classifier, metadata for learn, and its commands. From the credential schema alone the framework derives the auth flags, the environment variable names, the profile format, the status discover reports, and the exit-3 error when nothing is configured. From each command's declared metadata it derives policy enforcement, --dry-run and --confirm behaviour, and the introspection output.

npm run scaffold-provider -- --tier contributed --name acme --display "Acme Widgets"
npm run build && npx vitest run test/conformance

The conformance suite iterates every registered command and checks, among other things: complete and truthful safety metadata, examples that name nothing internal, error hints that name the command fixing the problem, a working --schema and --examples with an empty environment, and no imports between providers or from core into a provider directory. The full guide, with the pull-request checklist, is PROVIDER_AUTHORING.md.

Tenant catalogues and canonical names

aclif <provider> introspect --bootstrap captures an instance's custom objects, fields, and enumerations into a tenant catalogue, so learn and --schema answer in the customer's own names instead of the vendor's defaults. Alias sets map canonical entity and field names onto each provider and instance's native names, and --canonical resolves through them. A starter vocabulary ships with the framework; aliases import and aliases export move sets between installations. The formats are in CONTRACT.md.

Manifests

A declarative JSON manifest turns one HTTP endpoint, such as an Apex REST class or a ServiceNow scripted API, into a command with the same envelope, metadata, and introspection as a static one, without writing a provider. Manifests are loaded from the config directory standalone, or supplied by the host when embedded.
